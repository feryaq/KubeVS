# Расчёт производственной цепочки

`../scripts/analyze_chain.py INPUT.json` оценивает выбранный DAG. Это локальная модель: она не читает Minecraft и не заменяет live graph KubeVS. Формат: [schema.json](schema.json); пример: [shared-chain.json](examples/shared-chain.json).

- `recipes` задаёт один выбранный single-output рецепт на выходной item; item без рецепта считается сырьём. Byproducts не моделируются как дополнительные выходы: не включай их повторно в сырьевые итоги. Если byproduct используется в другом рецепте, учитывай его отдельно, не списывая тот же произведённый материал одновременно как сырьё и как повторный выход.
- Количества выхода/ингредиентов и целевой объём — положительные целые на партию. `chance` — вероятность независимого Bernoulli batch `(0,1]`.
- В `expected` для спроса `d` и выхода `q` нужно `k = ceil(d/q)` успешных партий; ожидаемое число испытаний до k успехов `E[N] = k/p`. Поэтому `batch_estimate` может быть дробным, а ингредиенты, время и EU считаются по ожидаемому числу испытаний. `output_units_at_threshold = k × q` показывает выход при достижении порога и не является гарантией для фиксированного числа запусков. Это ожидание времени остановки, не имитация распределения и не точное ожидание конечного surplus для иной политики запуска.
- В `guaranteed` допускаются только рецепты с шансом 1; `batch_estimate` — целое число требуемых запусков и отдельно указывается гарантированный выход. Рецепт с шансом ниже 1 недоступен для гарантированного плана.
- Скрипт строит граф только по consumed-ингредиентам и отклоняет цикл с путём. Катализаторы — отдельное требование запаса: их producer-рецепт не запускается, если item не нужен ещё и как consumed. Цикл графа не доказывает дюп; реальные возвраты и побочные продукты анализируй отдельно.
- Спрос на общий полуфабрикат агрегируется до округления партий. Запас катализатора — максимум количества, нужного на одной серийной стадии, чтобы допустить его повторное использование; это занижает запас, если стадии работают параллельно.
- При заданном целевом `items_per_second` спрос на каждом consumed item распространяется по рецептурной стехиометрии без округления партий. `steady_state_batches_per_second` и число машин рассчитываются отдельно для каждого рецепта по известным `ticks`, `chance` в expected mode и `parallel_per_machine`. Это установившаяся производительность, не оценка разгона или фактически измеренной нагрузки.
- `ticks`, `eu_per_tick`, `parallel_per_machine` указывай только по подтверждённым данным. Время: ticks / номинальные 20 TPS; энергия: EU/t × ticks × партии, без конверсии EU↔RF. Сумма секунд по цепочке предполагает последовательные стадии; это суммарная машинная работа, не wall-clock время. Неизвестные значения остаются неизвестными.

Для каскада вероятностных стадий распространение среднего спроса — приближение: `E[ceil(D/q)]` обычно не равно `ceil(E[D]/q)`. Оценка `k/p` точна для фиксированного спроса одной независимой Bernoulli-стадии; сквозной результат со случайным спросом и округлением не выдавай за точное математическое ожидание или доверительный запас. Для такой задачи нужна отдельно обоснованная модель распределений или симуляция.
