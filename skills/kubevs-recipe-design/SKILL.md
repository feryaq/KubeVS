# KubeVS recipe design

Create recipes that fit the pack's materials, machines, progression, and actual installed versions. Keep physical reasoning plausible without presenting game abstractions as real science. Distinguish **complexity** (meaningful steps, machines, materials, infrastructure) from **tedium** (repeated clicks, travel, waiting, arbitrary gates); add the former only when it creates a useful choice, and reduce the latter.

## Ground truth

1. Read resource `kubevs://guide` once per working context; call `kubevs_status` and inspect `kubevs_project_roots`. Reuse confirmed facts while the project and installed versions remain unchanged. Confirm Minecraft, KubeJS, integrations, and live Connector state. If MCP is unavailable, report that evidence gap and work only from provided files/docs.
2. Before cross-mod integration work, offer the user these three choices with short concrete descriptions: **a few shared recipes** (selective item/recipe links while each mod keeps its progression), **connected progression** (several meaningful cross-mod production links), or **unified progression** (a deliberately integrated progression across the relevant mods). Wait for the user's selection before making recipe edits whose scope or balance depends on this choice; independent inspection and research can continue meanwhile. If the user explicitly delegates the choice (for example, “реши сам”), choose the conservative few-shared-recipes option. Do not use elapsed time or silence as consent or as a fallback. Preserve explicit prior decisions and narrow requested fixes; do not reopen settled choices. Do not assume every installed mod should be merged or that GregTech should dominate.
3. Research the relevant mods in context before proposing integration. Confirm installed versions and each mod's purpose, intended gameplay loop, native machines, material progression, nearby recipes, configs/scripts, and intended role in this pack. Inspect enough adjacent content to understand what a change connects, bypasses, or strands. Prefer live project data and version-matched source/docs; distinguish confirmed facts from inference. Do not infer that similar item names or processing themes imply compatible progression.
4. Use `kubevs_list_registries`, `kubevs_search_registry`, `kubevs_tag_members`, and `kubevs_list_mods` to confirm item/fluid/tag/machine IDs and installed versions; use `kubevs_list_recipes`/`kubevs_get_recipe` to inspect actual recipes. Read schema definitions only for relevant serializers (`schemaId`); use `kubevs_craft_graph` when chain analysis is needed. Do not dump unrelated schemas, whole registries, or every advanced GregTech operation for a narrow edit. Research completeness means answering the design questions with evidence, not collecting the largest payload. Treat live results and version-matched source documentation as authoritative; never invent IDs, GregTech APIs, machine names, voltage tiers, overclock rules, or serializer fields.
5. For GregTech CEu 1.21.1, verify the exact installed mod/version and consult its live docs/source and actual machine/recipe data for every claimed mechanic. Record where each recipe form and machine is confirmed. If unavailable, make a clearly marked draft or ask for the missing source; do not silently substitute GTCEu 1.20 or other forks.
6. Keep model estimates distinct from measured runtime facts. State assumptions for yields, chance, time, power, parallelism, availability, and byproducts. Do not call EU RF or infer conversions without pack-specific evidence.

## Design and review

- Avoid duplicate MCP payloads: retain returned revisions and use `ifRevision` on repeat file, recipe, schema and graph reads. An `unchanged: true` response reuses the exact prior result; request without the condition if that result is no longer available. The default graph is lossless: `columns` describes node rows, `children` contains row indices, and `recipes` stores shared metadata once; request `format: tree` only if nested objects help. For a requested shopping list use `format: resources`; preserve and explain unresolved/truncated coverage rather than hiding it. Full schemas remain available by default; request only relevant `schemaId` or recipe JSON `paths` when the task needs those fields. Saved-file replies omit already-supplied code; `includeContent: true` restores it. Never save tokens by skipping mod research, balancing or runtime verification, or by treating partial evidence as a full audit.

- Place the recipe in the existing progression: check unlocks, earliest machine access, resource scarcity, adjacent recipes, and whether it bypasses or strands a mod's intended path.
- Give every ingredient and processing step a reason a player can understand. Prefer material transformations or a useful machine property over decorative ingredient piles and unexplained catalysts.
- Inspect the dependency graph for cycles, unavailable inputs, dead ends, bypasses, and balance across mods. State whether the graph is a complete catalog, a bounded/truncated tree, or partial because serializers or recipe forms are unsupported; missing edges in a bounded or unsupported graph are not evidence that no path exists. A cycle is a graph/design finding, not proof of a dupe; investigate item return paths, catalysts, chance, and machine behavior separately.
- Estimate raw demand only after aggregating shared intermediates. Guaranteed mode uses whole batches; expected mode estimates Bernoulli stopping trials and can produce fractional expected batch counts. Propagate steady-state rates through each consumed ingredient before sizing machines. Keep reusable catalyst stock separate from consumed inputs. See [chain-calculator.md](references/chain-calculator.md).
- Calculate time from recipe ticks using nominal 20 TPS, and energy from verified EU/t × ticks × batches. Label these nominal model estimates, not measured durations. Include machine count only when target throughput and relevant parallelism are known; otherwise leave it unknown.
- Consider byproducts, recycling, voiding, and all return paths. Check whether recycling can amplify material, whether chance products alter expected inputs, and whether outputs have a credible sink. Do not claim a dupe without demonstrating a repeatable net-positive loop under actual recipe semantics.
- Assess tedium with concrete evidence: number of distinct stages, repeated batches/clicks, travel, unattended wait, bottleneck, and whether automation removes it. Do not emit a numeric “tedium score” without grounded, agreed inputs.
- Present key assumptions and trade-offs briefly. For implementation, preview with `kubevs_generate_recipe` or the relevant supported generator (`save: false`); for GTCEu use `kubevs_generate_gregtech_recipe` with its native builder. Inspect warnings, IDs, schema, and graph. Before overwriting, call `kubevs_read_file`, then pass its exact revision to `kubevs_write_file` or the generator. Preview does not modify files. A save does not apply recipes in game: use `kubevs_reload` explicitly when permitted; startup registrations require restart.
- Do not trust lexical diagnostics alone to establish that a runtime recipe was changed. `replaceInput` may not traverse custom nested recipe JSON or serializer-specific structures. When it misses such structures, rewrite the affected recipe explicitly using the original recipe as the template and preserve all unrelated fields, conditions, IDs, and serializer data. After reload, inspect the exact runtime recipe JSON through the live recipe tools and confirm both the intended replacement and absence of the old unwanted ingredient/tag. If the serializer cannot be inspected or the live runtime result cannot be queried, report that verification limit instead of claiming success.
- After edits, inspect the resulting file and re-read/rebuild the graph. Report what was modelled, what came from live data, and what still needs an in-game check. Avoid large questionnaires; ask only when a missing choice materially changes progression or output.
